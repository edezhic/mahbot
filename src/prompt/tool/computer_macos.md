## macOS

* macOS 14 or newer (the product's floor); stills use ScreenCaptureKit, observe/act use the AX API. On an older macOS a still is `unsupported`.
* The three grants belong to the TERMINAL the daemon was started from, not to the product — a bare binary has no privacy identity of its own. The owner enables that terminal once under System Settings → Privacy & Security: Accessibility (tree reads and element actions), input sending (clicks, typing, key chords such as `cmd+shift+t` — macOS files it under the same Accessibility pane) and Screen Recording (stills). The grants survive rebuilds and self-updates because the terminal's signature never changes, and every process started from the same terminal — your own shell commands included — shares them.
* A missing grant is requested from the system when an action needs it; the dialog's subject is the terminal. Screen Recording applies only after mahbot is restarted, and macOS asks for it again periodically by design. There is no way around this and none is attempted. A missing grant surfaces as `permission-denied`.
* Never try to grant a permission yourself — a settings window is not yours to click.
* `type`, `drag` and `scroll` with a point on a named window are verified, not assumed: the window is raised and then checked to be the one the window server would deliver to. When it could not be brought forward the call fails with `degraded` and nothing was sent — click the window first, then repeat the action. A coordinate `click` is pointer input: the named window is raised when it can be, and the click lands on whatever is under its point.
* A minimized window is refused with `degraded` for a still, for coordinate input and for `observe` — it has no visible pixels, and its frame is the one it had before. Ask the owner to restore it.
* Windows on another Space, behind another app or minimized are all in the capture list; a still of a window that is gone reports `surface-gone`, naming what happened.
* The `screen` target is composited at the densest attached display's scale, so a laptop-plus-monitor arrangement produces one faithful image at uniform density.
* A tree keeps at most 2000 characters of a node's value and 200 of its name, and a window or application title is kept to the same 200. A longer one keeps its beginning, marked with an ellipsis, and the header states the cut (a cut title counts as a cut name) — the cap is on what mahbot copies in and keeps, not on what the application hands the system.
* A still is bounded by the product, not by what a display reports: one call may hold at most 134 megapixels (512 MiB of RGBA) at once, and the `screen` composite, the display frame being blitted and the zoom crop all count. A call that would need more is refused with `degraded` naming the ceiling — a clipped image is never returned instead, so `zoom` cannot deliver there either; a window still is captured on its own, so naming a window is the smaller surface that works. An ordinary display is far below the ceiling (a 6K display is 20 megapixels).
* mahbot's own window is an ordinary target: listed, readable, actionable and capturable. Its accessibility exchanges are performed on the main thread — the only place the system answers a request addressed to this process — so they can take a moment longer; if that thread stays busy beyond a bounded wait, a read fails with `degraded` naming it, coordinate input fails the same way before it has sent anything, and an element action comes back `applied but unconfirmed`, because the request may still land once that thread catches up.
* An element action is delivered, not verified: an application that cannot confirm the accessibility request gets `applied but unconfirmed`, so re-observe the target before acting on it again.
* No accessibility exchange can hold the call: mahbot sets the system's AX messaging timeout itself (10 seconds, never shorter than the default applications rely on), so a target that does not answer one exchange loses that attribute or that child — exactly as if it had refused it — and the walk continues. Each call's accessibility work is bounded as a whole: 120 seconds for an observation, 130 for an element action's (it observes first), 20 for a window listing or a surface lookup — resolution and the reads that name the surface included, and a 10-second share for any one application, checked before every read it makes, so it can overrun by at most the one read in flight: a hung one is caught and skipped, named as unread in the listing, while the healthy windows around it are kept — a skipped application is a partial answer, not a failed call. A budget that runs out ends the call with `degraded`, naming the window; retry then, or take a screenshot instead. A responsive target is unaffected — a 4000-node tree is about 36k exchanges and stays well inside the observation budget.
* Typing goes one character at a time, so an interruption part-way through reports `applied but unconfirmed` with how many characters were typed.
