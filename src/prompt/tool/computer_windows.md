## Windows

* No setup, no grant, no elevation and no signature: UI Automation for the tree and element actions, `SendInput` for pointer and keyboard, Windows.Graphics.Capture with a GDI fallback for stills. Trees are capped at 2000 nodes — the header reports the counts of what was read, so treat a very large count as a tree that may be missing its deepest parts and narrow the target.
* `cmd` in a chord is the WINDOWS key on this platform (`cmd+e` opens Explorer); `win` is also accepted as a key name for a plain Windows-key tap. `ctrl`, `alt` and `shift` mean themselves. Windows itself claims some Windows-key chords, so those act at the OS level before the target sees them.
* Input is posted to the foreground window. `type`, `click`, `scroll` and `drag` raise a window target first and refuse it if it is elevated; `type`, `scroll` with a point and `drag` also require that window to actually hold the foreground, and fail with `degraded` instead of reporting an input that landed elsewhere. With `screen` as the target there is no window to raise, so the check is on what the input touches — the window at the point for `click`, `drag` and `scroll` with a point, and the foreground window for `type`. A `scroll` without x/y names no surface at all: it is posted as a plain wheel event that the system routes to the focused window (or the hovered one, where the desktop scrolls hovered windows), and no window is raised on its behalf — its elevation check is the focused window's. `press` never raises anything: a chord goes to whatever already has focus, so click the window you mean first. A `click` by coordinates is pointer input: the point is mapped on the target surface, and the click lands on whatever is under that point.
* If typing, a `drag` or a `scroll` is refused because a window could not be brought forward, bring it forward yourself with `click { target, x, y }` on its surface, then repeat the action.
* Stills: Windows.Graphics.Capture draws its own visible capture indicator around what it captures. That is by design and cannot be removed — never try, and do not treat it as an error.
* Some applications return an all-black frame from the capture facility (protected content, a surface that refuses readback). The tool then tries the next route and, if every route is blank, reports `unsupported` with the causes; a blank image never comes back as a successful observation. Capture is per target and per route: one window failing says nothing about the rest.
* A minimized window is refused with `degraded: … is minimized — restore it first` for every action that addresses it (capture, observe, coordinate input); ask the owner to restore it.
* Windows owned by an elevated process cannot be driven from this non-elevated process — clicking or typing into one fails with `permission-denied` naming exactly that, and reading its tree comes back thin or `permission-denied` too (Windows blocks accessibility reads into it as well). A capture of such a window may still work. Starting elevated is out of scope; tell the owner instead.
* The UAC secure desktop and the lock screen are unreachable: actions fail with `degraded` naming them. Do not attempt workarounds; ask the owner to return to their desktop.
* A window that stops responding never hangs the product: the call gives up after a bounded wait and reports `degraded` with a timeout. `wait`, re-observe, or use `screenshot` before repeating an action — a retried click may otherwise apply twice.
* An element action uses the first accessibility action the element supports; only an element that supports none at all is clicked at its own point, as a user would. An action the element refuses (a disabled control) is reported instead of being retried as a click.
* The capture facility returns the window's own content even where another window covers it; the GDI fallback is a plain read of the desktop over the window's rect, so occluders are visible.
* mahbot's own window is listed, readable, capturable, and coordinate input reaches it. An ELEMENT action on it (`click`/`type` by `ref`) fails as `self-target: …` — not a permission problem, and no retry or other element changes it: this process cannot drive its own accessibility elements safely, because an element action is answered in-process and this backend has no way onto the interface thread. Reads, stills and coordinate input are separate operations and do keep working.
