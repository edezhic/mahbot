Greps this shell runs are served by the built-in engine rather than by a system program — single-file lookups included — so an empty result from a served search always means the search ran and matched nothing. A search the engine recognises but cannot serve fails as a tool error instead of being reported as "no matches": a grep nested in another command (another interpreter's command line, `xargs grep …`, `find … -exec grep … +`, a second grep member of a pipeline), an unsupported flag, a redirect glued to one of the search's own words (`grep -n x>out.txt f.txt` — spell it `grep -n x f.txt > out.txt`), and a `cd` the engine cannot track. Left to the platform as written, neither served nor refused — the platform's own program runs, and its outcome is what you see, never an empty match set from this engine: a search another program owns (`git grep …`, `docker run … grep …`, `ssh host grep …`), a search in the argument list of a program the engine does not list (`foo grep x`), a search whose program is spelled with a path (`.\grep …`), a grep word glued to a `{` or to a redirect operator (`{grep x f.txt`, `grep>x f.txt` — the command word is then not a search), and `find … -exec grep … \;`, whose `\;` stops the engine's reading before it reaches the search. Double-quote the search's arguments: `'`, `^`, parentheses and `;` are read differently by this interpreter, and a command using one of them outside quotes may be refused. A single word carrying two `%` characters is refused as well: this interpreter expands `%…%` before any program runs and quoting does not stop it, so the reading is deliberately wider than that pairing and refuses `100%%` too. A single `%` and every `!` are taken literally.
