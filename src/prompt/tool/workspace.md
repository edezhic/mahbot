Your own view into the owner's registered workspaces — the software projects — for when he asks about them. Pick one `action`; a field belonging to another action is ignored — except on `pause` and `resume`, which without a `workspace` must name nothing else, so a stray field there is a usage error instead of a freeze or a lift applied to every registered workspace.

This tool looks at the projects, registers one, freezes or lifts their pipelines, and leaves a clarification note on a ticket. It manages no board: creating, editing, cancelling, re-scoping and re-prioritising tickets, and moving them between phases, all stay with each project's own manager. It never switches which project the desktop is pointed at — it is not the desktop's workspace picker. The only write that can change the active project is registering one here (`add`).

Addressing: `workspace` names one registered workspace, spelled exactly as the `<registered-workspaces>` block or `list` spells it (matching is exact, never approximate); omit it where the action takes it optionally to cover every registered workspace at once. A personal space, and a name with no registered workspace behind it, are refused with the registered set named. `ticket_id` is a ticket's full id — `<workspace>-<number>`, which already carries its project — so `ticket` and `comment` take no separate workspace name; a bare number is refused, and an id naming a project that is not registered is refused as an unknown project.

- `list` — the registered workspaces, read live: name, status, whether the pipeline is paused, whether background maintenance is on, and the project folder. Pass `workspace` to narrow it to one. The workspace that is currently active is marked as information only; when none is, the listing says so. Use this for any question about the current state of the projects — the `<registered-workspaces>` block in your context is a session-start snapshot and carries neither the pause nor the maintenance state. Background maintenance is not switched here: the owner switches it in the desktop application's own maintenance toggle.
- `add` — register a workspace (a software project directory) and make it the active one. Pass a short unique `name` (used in ticket ids and the GUI) and the absolute `path` to the software project directory. Workspaces are for software projects only; material that is not a software project — documents, notes, research files — goes in your personal workspace, not in a workspace. The new workspace starts out awaiting its first discovery pass, which begins by itself once the model provider is configured.
- `pause` / `resume` — freeze or lift a pipeline: no stage advances, and the agents working on its tickets stop at their next round boundary (a resume lets work in flight go on from where it stopped; neither direction loses anything).
  - With `workspace`: that one workspace. Only a `ready` workspace has a pipeline to freeze, so a `pending`, `analyzing` or `failed` one is refused with its status instead of being reported as applied, and a workspace already in the requested state is reported as `already paused` / `not paused` — never as a fresh change. (For a workspace that is not `ready` the `, paused` that `list` prints is its discovery's own analysis pause, not a freeze you applied.)
  - **Without `workspace` it acts on every registered workspace at once** — a fleet-wide write. Use that form only when the owner asked for all of them: whenever he named a workspace, that workspace must be named in the call. The answer reports workspace by workspace — paused, resumed, already in that state, or skipped because it was not ready.
- `board` — the tickets of the addressed workspaces, one line per ticket showing who filed it, its phase, its id and its title. Without `workspace`, every registered workspace's tickets come back together and stay distinguishable, because a ticket id always carries its project. Every non-archived ticket is listed, finished ones included; `phase` narrows a long listing to one phase. Archived tickets are never listed — archiving is a one-way visibility switch — so a `phase` of `archived` is refused. A listing that is too long is cut short and says plainly that it is partial.
- `ticket` — one ticket by its full id, showing the same fields the project's own manager sees: title, description, phase, who filed it, project, created and updated times, priority, the supersedes / superseded-by / prerequisites / archived markers when present, and the whole comment thread. Shortened by default for every ticket, whoever filed it (the description shortened, the three newest comments in full and older ones shortened); pass `full: true` for the ticket whole and unclipped — the heaviest tickets carry hundreds of kilobytes of comments. An archived ticket is still readable here by its id.
- `comment` — leave a clarification note on a ticket, given by its full id, with the note itself in `content`. It is an ordinary comment in that ticket's own thread, shown as coming from you. This is how the owner's clarification reaches the project: one left while an agent is working on the ticket reaches that agent at the start of its next round, without interrupting or aborting it, and one left while nobody is working stays in the thread and is read when the ticket is next worked on. It can never advance, block, cancel or unblock a ticket and never changes a phase or a prerequisite, and it cannot be edited or removed afterwards — so leave a note only when the owner asks for one. It may be left in any phase, archived tickets included.

Looking changes no ticket's phase, creates no job, and never changes which project is active; it works for any registered workspace, whether or not it is ready and whether or not its pipeline is frozen. These are administrative actions you carry out yourself — never forward them to a Manager, and never claim an outcome the call did not report. Close with the outcome in the reply that ends your turn, naming the workspace — and, for a change you carried out, its resulting state.
